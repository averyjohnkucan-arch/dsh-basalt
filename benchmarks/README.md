# Inference tuning protocol and source snapshot

This directory preserves the actual Linux harness used to compare saved profiles with custom Basalt, custom NInfer and Strata. It is an audit snapshot, not a turnkey benchmark distribution. `source-manifest.json` gives exact source hashes. The sources retain the NVMe scratch paths and sibling engine/plugin checkout layout used for the runs. Configure those paths, exact artifacts, native libraries and fixture inputs for another machine. Never point the rotation scripts at original model weights.

Tuning remains in progress until each family has a matching performance receipt, real-plugin GPU receipt, and final report. Source publication does not establish a completed tuned release. Small compatibility probes, restored-prefix screens and interrupted attempts are not final throughput evidence.

## Final measurement convention

- Low context: exactly 8,192 native-chat input tokens containing code.
- High context: floor(80% of native context capacity), separately for text, conversation and original-story generation. This is 209,715 input tokens for the tested Qwen models and 838,860 for DeepSeek. This convention supersedes the earlier 10%/90% all-code diagnostics; the earlier measurements remain separate evidence.
- Generate 8,192 tokens and time the final 4,096 for sustained decode. HTTP draft-batch timing boundaries can differ by up to seven tokens; actual token counts are retained.
- Thinking off, temperature zero, seed 42 where supported. Tokenizer-native chat framing is used. Exact prompt length and token hash are recorded. Model-native tokenizers must be checked before sharing fixtures across artifacts.
- Fresh worker and no restored prefix for qualified prefill. OS file cache is not globally dropped. Restored-prefix screens are explicitly diagnostic.
- RTX PRO 5000 Blackwell Laptop GPU, 95 W requested/default power. The enforced limit varies under load (55 W was observed); it is not a fixed 95 W draw or enforced limit. CPU affinity and native arguments are retained in each result. Inference weights come only from the NVMe.

The peak long-decode preset maximizes the minimum sustained decode across the three genre medians. The prefill phase then maximizes minimum cold prefill while retaining at least95% of EACH genre median from that peak-decode preset. A minimum-only prefill floor could hide a larger regression in another genre, so the per-genre floors are mandatory. Absolute limiting genres are repeated; when controls differ, the genre with the smallest relative retention is repeated for both presets. This protects the prefill tradeoff relative to the peak worst-case preset; it does not claim one configuration reaches every genre's independent maximum. Free continuations can differ across settings and change draft acceptance, so a finite workload range is not a universal throughput guarantee.

A separate peak-code preset is retained when it uses different controls. Its context capacity stays fully configured; it receives its own high-context genre measurements. Diagnostic 2,048-output screens rank candidates; final low-code candidates receive repeated full 8,192-output measurements. The peak is the best measured sustained-code median, not an assertion that every possible configuration has been exhausted.

The search also compares the user's saved expert ranking against Basalt's shipped ranking. The saved Basalt-format ranking is byte-identical to the user's Strata ranking after removing the four-byte STRP wrapper, and it differs from the shipped file. Explicit ranking inputs are copied into each native benchmark's own directory; a worker cannot mutate the source snapshot. The learned ranking is tested as a long-context and low-code candidate rather than assumed to be faster.

## Evidence and profile labels

The model and profile names use `... - pLOW/dLOW - pHIGH/dHIGH`. Each pair comes from the same actual measurement. The high pair comes from the slowest actual selected-settings genre/repeat, rather than combining the fastest prefill from one run with decode from another. The metadata retains the complete measured range, native configuration, binary and artifact fingerprints, and host-memory evidence.

Performance qualification, actual DSH-adapter GPU serving, generated-code quality and source/binary publication are separate gates. A native timing receipt alone does not prove plugin functionality or answer quality. The main comparison has exactly three columns: model name, old settings speed, current Basalt speed. NInfer and Strata results stay in separate comparisons. Unsupported Basalt artifacts are labeled explicitly.

The generated-function checks run the model's output unmodified inside Bubblewrap without home-directory or network access, with CPU and memory limits. A retained LRU-ordering failure means the small code suite is not wholly passing. Numerical kernel references and this small generated-code suite do not establish full BF16-reference model quality, vision support, or portability to untested architectures.

`audit_range_outputs.py` separately inspects the actual selected continuations offline, verifies their token hashes, and records exact repeated long paragraphs and duplicate 16-token windows. Repetitive free continuations remain in the measured performance range. A high throughput observation can include repetitive output; it must not be presented as a guarantee of good conversational or story quality. Schema 2 keeps the exact-long-paragraph and repeated-token-window flags separate: zero identical long paragraphs does not mean an output has no repeated section patterns. Repeated token windows can also be legitimate shared phrases, so neither diagnostic alone establishes a semantic quality failure. These diagnostics are separate from the generated-function checks.

## Power-policy recovery and benchmark cohorts

The laptop initially reported desktop `performance` while its actual firmware profile was `balanced`; the matching installed `nvidia-powerd` service had crashed at boot. A running long-context test showed a 55 W enforced GPU limit despite a 95 W requested/default limit. With no inference worker active, restarting that service and reapplying the existing performance selection restored firmware `performance`. The subsequent full matched experiment observed a dynamic enforced limit of 95–110 W.

The same executable, model, native arguments and exact 209,715-token prompt measured prefill 1,562 → 3,091 tokens/s and sustained late decode 54.0 → 71.8 tokens/s. Both generated 8,192 tokens and timed the final 4,096. Continuations differed, and the daemon/profile changes were applied together; this is one observed experiment, not a universal hardware-only or engine-only speedup. `evidence/power-policy-matched-comparison.json` retains the exact paired values and qualification.

Final old/new comparisons are rerun together in the fresh `performance-powerd-20261115` cohort. Historical results remain available but cannot enter the new selection: environment identity participates in configuration identity, case paths and repeatability plans are distinct, and power preconditions are checked before and after new runs. Telemetry now records the enforced/default limit as well as the firmware profile. A 95 W requested/default value must never be described as a fixed enforced limit or constant draw.

`refresh_range_metrics.py` closes both saved presets over all completed, uncached, guarded 8,192-output observations at the same controls and exact workload depth before the performance gate. This includes repeats acquired while testing the peak-code candidate against the long-context preset, so a slower repeat cannot be omitted from a separate profile's high-context range or paired name. A real-data regression retains the corrected 65.9 to 64.5 tokens/s minimum without changing engine controls.

The serial queue records per-job completion, environment identity and a job-plan hash. `DSH_QUEUE_START_INDEX` resumes only past proven completed jobs; `range_queue.py 0 --plan` validates a requested boundary without launching inference. The first recovery can seed only the three completed Flash jobs from matching native-performance and actual-adapter GPU receipts; an incomplete hybrid job cannot be skipped. Previous matrix-completion receipts are archived before a resumed pipeline begins.

Hybrid memory fits keep the 96/108 GiB worker high/max limits and pressure guard unchanged. A 64-output fit uses the full 80%-context text prefix and establishes compatibility only; it is not a final speed measurement. The initial 96 GiB resident budget hit the pressure guard with no OOM kill. Successful budgets become candidates for the ordinary sustained tuning pass, while failed attempts and original settings remain preserved.

Resume validity is checked against the completed result's actual inputs, including normalization of owned expert-ranking copies. Replacing an attempt archives its previous result and removes that success from the active case before launch. Truncated or malformed attempt/input JSON is also archived and rebuilt, retaining the original bytes. A failed post-run power check marks the completed measurement unqualified, preserving its data and forcing a new attempt on resume. `benchmark_resume_validity_test.py` exercises these paths with simulated workers and real scratch-file operations; an optional old `range_common.py` argument reproduces the prior failure. The completed performance-cohort audit confirms that existing accepted cases matched their planned inputs and reached controller `END ... ok` after their post-run checks. This fixes benchmark recovery validity; the earlier OOM repair remains the separate RAM-isolation work.

With Dynamic Boost active, this driver can report the requested-power field as `N/A`. The plugin validation receipt preserves that as `null` and checks the available 95 W default, 110 W hardware maximum and current enforced reading. It does not invent a requested-power measurement when the driver omits it.

For this session the recovery used `sudo systemctl restart nvidia-powerd`, then `sudo powerprofilesctl set balanced` and `sudo powerprofilesctl set performance`. No driver replacement, reboot, manual overclock or clock locking was applied. This repaired the current session; a persistent fix for the daemon's boot-time crash is not established. [NVIDIA's Dynamic Boost documentation](https://download.nvidia.com/XFree86/Linux-x86_64/580.173.02/README/dynamicboost.html) describes the daemon's CPU/GPU power-budget role.

## Memory isolation

The original interrupted run shared the application's process group. Linux memory-pressure handling terminated that whole group. New workers have separate owned systemd scopes: MemoryHigh 96 GiB, MemoryMax 108 GiB, MemorySwapMax 1 GiB. A watchdog stops a worker when host available RAM falls below 12 GiB or memory-pressure avg10 exceeds 40% for six seconds. Cleanup stops the whole owned scope, including detached native descendants. The controller survives worker failure. These are host-specific limits; choose appropriate limits before running elsewhere.

`native_bench.py --config CONFIG.json` and `http_bench.py --config CONFIG.json` run one explicit native command and preserve token timing, logs, memory telemetry and paired rates. `benchmark_prompts.py` accepts an exact token-ID prompt or a prefix/body/suffix fixture. The tuning controllers require the fixture manifest and baseline configurations in the scratch layout. `prepare_range_fixtures.py` documents the original tasks and framing. Source novels are public-domain Project Gutenberg texts; their URLs and hashes are in `evidence/prose-corpus-sources.json`. Neither model weights nor full prompt/token fixtures are bundled here.

Derived model packs may be rotated only after the relevant performance and plugin checks complete, with reconstruction recipes retained. This avoids holding every duplicate conversion on the 2 TB NVMe at once. Original source weights are never deleted. A profile whose derived pack has been rotated is unavailable until that exact pack is reconstructed; retained rates do not imply the pack is currently installed.

## Hybrid pack recovery and guarded memory experiment

The original mixed-expert folder contains only `experts.bin` and `native_experts.txt`. `hybrid_strata_pack()` creates a scratch-only symlink overlay with the unchanged Flash base dense/index/tokenizer components and the hybrid expert pair. It validates all 48 independently typed layer ranges before launch. Original files are unchanged.

Hybrid-only experiments use MemoryHigh104GiB, retaining MemoryMax108GiB, SwapMax1GiB, host reserve12GiB and the same pressure watchdog. An explicit memory-policy identity separates these observations from default96GiB-high runs; the policy follows exported profiles into real-adapter verification. Short fits are compatibility screens. Full8192-output runs, repeats, quality checks and performance receipts remain required. `resume_hybrid_pipeline.py` waits for the corrected original96GiB fit, checks latest Strata separately, then resumes the57-job queue at index3 without replaying qualified Flash work.

The full-output Basalt hybrid startup also retries smaller resident budgets after an explicit RAM-watchdog stop and reruns all three genres. Non-memory errors stop immediately. Failed attempts stay archived, and short-fit budgets that fail sustained generation are excluded from the subsequent RAM candidates. The original saved Strata baseline is not modified by this recovery. `test_hybrid_sustained_fit.py` fault-injects the actual control-flow block without launching inference.

## Cross-model progress overview

`range_model_progress.py` renders all six supported Basalt model/KV families and keeps pending rows explicit. Each plotted range is recomputed from complete, uncached, RAM-isolated 8192-output text/chat/story observations in the active hardware cohort; short fits and individual unfinished tuning runs are excluded. Saved and qualified-current ranges stay separate. Every native qualification updates this overview, while the original Flash-only genre chart remains available.
